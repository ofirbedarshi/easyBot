# How the Builder works

Describes the Builder as implemented on 2026-10-26. Questioning is model-driven, except for a short list of **required topics** the application asks itself (see "Required topics" below). Prompt text tells the model what to do; it does not guarantee the model will do it. Only the application checks below are enforced.

## What it does and produces

The Builder interviews the business owner in chat and fills a draft business profile. The first owner message in an empty BUILD chat only wakes the bot: the app discards that text and replies with a fixed welcome (`openingMessage` in `src/builder.js`: product intro, a line that the Builder will ask a few short questions, early-access rough edges, then an invite to describe the business; paragraphs are separated by blank lines so they render on WhatsApp and in the web chat). The next message starts the interview. Later replies come from the model (`OPENAI_BUILDER_MODEL`, else `OPENAI_MODEL`, otherwise `gpt-4.1-mini`) using OpenAI structured outputs (strict `json_schema`). The Business Bot still defaults to `gpt-4o-mini` (`OPENAI_MODEL`). A 12-run replay of a two-turn interview found `gpt-4o-mini` still dropping some stated facts after the schema/delta change; `gpt-4.1-mini` captured them in every run. The model returns a **delta**: each draft field is null (or a reset flag is false) when the owner's current message did not set or change it. Code merges that delta into the stored draft. `newFacts` is a required top-level array (empty if none), not a draft key. Localhost `/api/start` leaves the chat empty until that wake.

The draft can hold: business name, what the business does, **ownerGoal** (the bot goal: `answer_questions` | `collect_details` | `answer_and_collect` | null) plus **ownerGoalRequested** (the owner's own words, kept for demo research only), services (name, price, notes), hours, location or service area, common customer questions (FAQ), information the bot should collect from the customer (intake), explicit unknowns, and **conversation settings** (behavior — not business facts): **tone** (free text), **responseLength** (`short` | `standard` | null), **priceDisclosure** (`relevant` | `on_request` | null), and **assistant identity**: **assistantName** (free text | null) and **openingMessage** (owner's opening text | null). Unknown text fields are stored as null. `ownerGoal` stays null until the owner answers the goal question — the app never invents a goal. Any other stored value (including legacy free-text goals) is normalized to null on load, merge, and use, so it is never shown or sent to the Business Bot. `ownerGoalRequested` is copied on approval but never reaches the Business Bot or the review. `commonQuestions` is an array of `{ question, answer }` objects: `question` is what customers ask; `answer` is the owner’s explanation the Business Bot may tell customers. Legacy bare strings are normalized on load/merge to `{ question, answer: "" }`. Only FAQ items with a non-empty `answer` are injected into the customer prompt as approved facts. `informationToCollect` uses a different convention: **null** means the owner has not been asked yet; **[]** means the owner said collect nothing; a non-empty array lists the items. Each turn saves that draft. Live approved fields change only when the model marks the turn approved and the minimum below is met. Approval writes the profile (with `approvedAt`); the Business Bot is live at once and its customer prompt is built from those approved fields: approved business facts (identity, services, hours, location, FAQ answers), explicit unknowns, intake whitelist, `ownerGoal` as one fixed BOT OBJECTIVE sentence per value (`OBJECTIVE_SENTENCES` in `customerPrompt.js`; conversational direction only, collecting is limited to the intake list), and — separately — conversation settings (tone, reply length, price disclosure).

**Conversation settings defaults (enforced on read/use, not written into stored nulls):** when `tone` is null, effective tone is `friendly, clear, and professional`. When `responseLength` is null, effective value is `standard`. When `priceDisclosure` is null, effective value is `relevant`. Invalid enum spellings are normalized or dropped to null on load. Legacy profiles without the new keys load safely and keep any existing `tone`. When `assistantName` is null the Business Bot has no name (the app never invents one). When `openingMessage` is null the customer prompt tells the Business Bot to give a short introduction as the digital assistant of the approved business name (or "this business"). There is no fixed default opening text.

**Assistant identity (prompt, not enforced):** the customer prompt tells the Business Bot to say openly that it is a digital assistant and never to present itself as the owner or a human. It uses the opening only in its first reply of a **fresh conversation**, meaning a TEST conversation with no earlier turns in its history. Each `/test` starts a new, empty conversation. The model receives only the last 20 stored messages, so in a very long conversation the first reply eventually falls out of what it sees. If the first message is a real question, the Business Bot should open and answer it in the same reply, and should not re-introduce itself later. The app does not inject the opening; this is model behavior driven by chat history. The opening is customer-facing wording only. It cannot establish facts, prices, capabilities, or intake, and it does not override the price policy. Conflicting parts are to be left out.

**Explicit identity reset (enforced on merge):** an omitted, null, or blank `assistantName` / `openingMessage` in the draft preserves the live value. To clear one back to its default, the draft carries `assistantNameReset: true` / `openingMessageReset: true` with a null value. `reconcileDraft` keeps a pending reset flag across later turns until a new non-empty value replaces it. `mergeDraft` applies the reset on approval. The prompt tells the model when to set these flags (an owner asking to remove the name or restore the default opening); whether the model does so reliably is **unverified**.

**Price disclosure / reply-length labels (single source):** owner-facing wording for the enums lives in `PRICE_DISCLOSURE_LABELS` and `RESPONSE_LENGTH_LABELS` in `profile.js` (`relevant` → “when useful and relevant”; `on_request` → “only when the customer asks about pricing”; `short` / `standard` as themselves). `formatSummary` and the Builder system prompt both read those maps so the explanation, pending draft, and approval summary stay aligned. Customer-prompt policy text in `customerPrompt.js` is separate (written for the Business Bot, not the owner).

**Price disclosure policies (only two):**
- `relevant` — mention approved prices when useful; do not dump prices into unrelated answers; volunteering a price in every general description is not required.
- `on_request` — mention prices only when the customer asks about pricing/cost/quote/total (or a clear pricing follow-up such as “And how much?”). A general description or booking request alone does not trigger prices. A prior pricing answer does **not** permanently unlock disclosure for later unrelated questions.

**Demo scope (prompt):** the customer bot may answer from approved facts, clarify needs, collect listed intake in chat, and confirm those details back. It cannot book calendars, take payments, or sync a CRM. An approved fact may describe a business process (for example that the owner confirms bookings); that does not mean the bot booked or contacted anyone. The system does **not** persist or deliver customer inquiries to the owner. Collect means ask and confirm in this conversation. After listed details are in the chat — including if the customer then asks whether they are booked — confirm or restate those details; do not claim a booking and do not send them to the owner because this chat cannot book. Owner redirect is for a real missing fact only. If approved facts give a pricing process instead of a number (consultation, quoted in person), that process is the complete answer — not an unknown price.

**Capability catalog (single source):** `CONFIG_CAPABILITIES` and `DEMO_SCOPE` in `profile.js` list every configurable field — what it represents and what it cannot represent — plus what the Business Bot can and cannot do. The Builder prompt renders both. Business facts include `otherFacts` and customer-facing policies (including how an offering is priced or quoted). A global never-mention-any-prices policy is still unsupported `priceDisclosure`; a per-offering quote or process rule is a fact. Per-message scripts, formatting or emoji rules, fixed sign-offs, language rules, reminders, and other actions stay unsupported.

**Configuration requests (prompt + enforced):** classify style, global price mention, identity, goal, intake list, and actions the bot should perform. What customers should be told — including what to say or not quote about an offering — is a business fact, not a config request (store it; do not refuse it as unsupported). For each classified request the Builder returns `configRequests: [{ request, status, field, alternative }]`. `request` must quote the owner's words; `status` is `supported`, `ambiguous`, or `unsupported`. Prompt: supported → update the field and describe it as proposed (live only after approval); ambiguous → ask one short question; unsupported → say so, offer the closest supported alternative by name, and wait for the owner to accept. Never say an unsupported request was added or noted. Accepting an offered alternative makes it a new supported request.
Enforced by `enforceConfigRequests` after each real Builder turn:
- A `supported` request that carries an `alternative` counts as unresolved.
- The field named by any unresolved request is restored to its previous draft value.
- If any request is unresolved, every setting field (tone, responseLength, priceDisclosure, assistantName, openingMessage) that changed this turn without a supported request naming it is restored too.
- If any request is unresolved, the turn is not ready for review.
**Not enforced:** the model's classification itself. If it marks an unsupported request as `supported` with the right field, the change goes through, though it still needs review and approval. Invalid enums are still dropped by `reconcileDraft`.

## What it asks

Nothing in code is labeled mandatory, optional, or conditional except the required topics and the approval-minimum name rule below. The prompt tells the model to start with the business only (invite them to tell about the business — not a feature checklist), and after the owner shares a real business detail to react in one short specific sentence that names what they said (not a generic "Great!" / "Got it") and then ask exactly one question. This reaction-then-question shape is prompt-only — **unverified** that the model always does it. It also tells the model to defer `ownerGoal` until `draft.name` is set, help vague goals without inventing `ownerGoal`, absorb one-message dumps (react specifically, then one follow-up), allow mid-setup direction changes, and for unsupported requests clearly refuse and offer an in-scope alternative. It also discovers topics **when relevant** (partial information is fine):

- Business name (required for a first bot — the model must not invent it)
- What the business does
- Owner goal for the bot (`ownerGoal`) — only after name is set
- Services and offerings
- Prices, if the owner has them, and how a price applies when that matters (per unit versus flat or per booking)
- Opening hours or availability
- Location or service area
- Common customer questions (FAQ: each entry is a customer question plus the owner’s answer; the Business Bot may use those answers as approved facts) — **required topic**
- Information the bot should collect from the customer (intake: name, phone, preferred day/time, and similar; the Business Bot asks for these in chat) — **required topic**
- Conversation settings when mentioned: tone, reply length, when to mention prices, assistant name, opening message (optional — defaults apply if the owner says nothing)

**Owner goal question (prompt only).** Once the name is set and `ownerGoal` is null, the prompt gives the model a fixed question (`OWNER_GOAL_QUESTION` in `builder.js`): "What's the main thing you'd like your bot to do for your business?", with examples (answer customer questions, help increase sales, collect contact details) and an invitation to answer freely. The model must not phrase it as "outcome" or "customer bot". The context hint also reminds the model to ask it next while `ownerGoal` is unset, unless the owner is mid-correction or changing a setting.

**Bot goal mapping.** The Business Bot supports only two things: answering questions and collecting the listed details. So `ownerGoal` holds one of three values (`OWNER_GOAL_VALUES` / `OWNER_GOAL_LABELS` in `profile.js`): `answer_questions`, `collect_details`, `answer_and_collect`.
- Prompt: the model copies the owner's words into `ownerGoalRequested` and maps the answer to a value. Answering questions and/or collecting details — including taking a message when someone wants to book — gets the matching value and `goalSupported=true`. Only calendar booking, payments, CRM, or outbound follow-ups get `answer_and_collect` and `goalSupported=false`.
- Enforced (`applyGoalSupport` in `builder.js`, part of `applyReviewGate`): a goal is unsupported only when the model says `goalSupported=false`. The app then stores `answer_and_collect` and replaces the model's text before its next question with a fixed line that states the mapped goal (`GOAL_FALLBACK_DISCLAIMER`: "I'll set the bot to answer questions and collect details."). It does not say a capability is unavailable. The owner's wording is not inspected. The line appears only on that turn, never in the review.
- `reconcileDraft` keeps the previous value when the model sends an invalid or empty goal. `ownerGoal` is not required for review.
- **Unverified:** that the model maps supported wording (including mixed “take a message / book” phrasing) to the right one of the three values, and that it flags only the demo-cannot operations.

For a proposed opening, the prompt tells the model to check it against the draft facts, demo scope, and price setting. If the opening claims an unsupported capability (such as booking), states an unapproved fact or price, impersonates the owner or a human, or contradicts the price policy, the model should explain the conflict, keep the previous opening in the draft, skip review, and ask for a correction. This is prompt-only (no app check). In one focused run it worked for a booking-claim opening.

The prompt tells the model to keep FAQ items in `commonQuestions` as `{ question, answer }` (full answer text when the owner explained it — not topic titles alone) and intake items in `informationToCollect`, and not to mix them. It also tells the model to clarify ambiguities that would change a customer answer: pricing basis or units, discounts, what a service area covers, hours edge cases, cancellation or refund policy, and booking or availability rules. It says capacity or group size does not settle how price scales. Setting and capability requests follow the capability-honesty rules above (clarify / refuse+offer / propose-then-approve). Whether any of these questions actually appear depends on the model and the conversation. **Unverified:** that the model always stores the full owner answer in `commonQuestions[].answer` rather than a truncated paraphrase, always leaves `ownerGoal` null until clarified, always maps natural-language style/price-disclosure requests into the enum fields correctly, always refuses unsupported capabilities cleanly, always keeps proposed vs applied distinct in its wording, and which clarification questions it asks in a given interview.

Application checks (enforced):

1. **Approval minimum** — `hasEnoughForFirstBot` is true when there is a non-empty business **name**, and there is at least one service or a description of what they do. A description alone cannot pass. A name with no description and no service cannot. Hours, location, prices, common questions, tone, responseLength, priceDisclosure, unknowns, `ownerGoal`, and a non-empty intake list are not required by this check.
2. **Required topics before the first review** (`REQUIRED_TOPICS` in `src/builderTopics.js`, checked in `applyReviewGate`). The list, in asking order:
   - `commonQuestions`: fixed question "What questions do customers usually ask you, and what do you answer? Share a few in your own words — or say skip if you prefer not to now." It is **skippable**: it counts as settled once the draft has at least one FAQ entry with an answer, or once the app has asked it and the owner has replied (anything, including "skip"). The app asks it once.
   - `informationToCollect`: the fixed intake question ("Before we finalize: should the customer bot collect any information..."). It is **not skippable**: it is settled only when `informationToCollect` is an array (`[]` for none). If the owner's reply leaves it null, the app asks again.

   When a turn would present a review (model `readyForReview`) and a topic is still open, the app does not present the review. It keeps the first non-question acknowledgment sentence of the model's text, appends that topic's fixed question, and records the topic in `draft.askedTopics` (app-owned; `reconcileDraft` carries it over and the model never sets it). One topic per turn.
   If the model asks an open topic in its own words (it reports `askingTopic`, and for FAQ the app also matches the wording of the model's question sentences), the app keeps the model's text up to its first question, replaces the rest with the fixed question, and records it as asked. This prevents asking twice when the owner skips. On the turn after a fixed question, the model gets a hint telling it how to store the answer.
   Required topics apply only before the first approval. An approved profile is never blocked by them. To make the Builder ask a new topic, add an entry to `REQUIRED_TOPICS`.
   **Unverified:** that the model always sets `askingTopic`. If it asks FAQ in wording the matcher misses and the owner skips, the app may ask FAQ once more.
3. **Draft reconciliation** — after each Builder turn, `reconcileDraft` normalizes `ownerGoal` / `responseLength` / `priceDisclosure` enums and preserves prior settled `informationToCollect`, `ownerGoal`, `tone`, `responseLength`, `priceDisclosure`, `assistantName`, and `openingMessage` when the model omits them, blanks them, or sends an invalid value (identity fields clear only via the explicit reset flags above). A style-only edit therefore cannot wipe an approved price-disclosure policy via a null draft field, and an opening-only edit cannot wipe the assistant name.

Seeded or hand-written profiles that omit `informationToCollect` are treated as nothing to collect when building the customer prompt; they do not go through the interview gate.

## Follow-ups and “enough”

The prompt tells the model that after the owner shares a real business detail, it should react in one short specific sentence that names what they said (not a generic "Great!" / "Got it"), then ask exactly one question; not repeat answered questions; and not bundle two asks. This reaction-then-question shape is prompt-only — the application does not count questions, check the lead, or pick the next one (**unverified** that the model always reacts specifically or asks only one). It does send the current draft and a hint: business name still required, enough may already exist for a first bot, or basics still missing (name plus offering/description). Right after a fixed required-topic question, it also sends how to store that answer.

The prompt tells the model to set ready for review once there is a non-empty business name plus at least one offering or a clear description, even if required topics are still open (the app asks them first), and to reply with **one short specific sentence about what they just said** (not a generic "Got it") — no summary, no questions, no bullet list, no "ready for review" (the app shows those). This enough-for-first-bot line is also prompt-only. Code does not turn that hint into ready-for-review by itself, except for settings-only edits (below). The model also sets `wantsReview` when the owner asked to see the current bot, summary, or review (schema field; **unverified** that it is always set). **Review presentation (enforced, `renderReview` in `ownerNav.js`):** whenever a turn ends in review (the model set `readyForReview` or `wantsReview`, or the app forces a settings-only review), the reply is:
1. The model's acknowledgment cut down by `reviewAck` to its first sentence that is not a question, a bullet/numbered line, a line ending in `:`, or review filler (review / summary / approve / set up / ready / prepare / below). It may be empty. **Enforced:** that line is prepended only when this turn changed the pending configuration (`draftReviewKey` before vs after). A turn that only re-presents the same draft shows the summary and options with no model line in front.
2. **First-time or unchanged:** "Here's your bot for {name}:" then one `Label: value` line per item (`summaryLines` in `ownerNav.js`): Business info, Services (name and price, no notes), Area, Hours, Not decided (only when there are unknowns), Other facts (`otherFacts` joined with `; `, only when there are any), Bot goal (the label of the stored value), Asks customers for, Q&A (count of answered entries), How the bot talks (tone / reply length / price setting / assistant name / custom opening, or "default"). Values are shown in full (not clipped), so a long services list stays visible in WhatsApp. Gaps are shown: empty area or hours read "not set (bot refers customers to you)", and empty Q&A reads "none yet (bot refers customers to you)". No markdown bold.
3. **Already approved with a pending draft:** "Here's what will change:" then only the changed lines in the same format, each with `(was: old)`. If the change is hidden by the short summary (e.g. a service note or a FAQ answer), the line ends with `(updated)` instead. Unchanged lines are not repeated.
4. "What would you like to do next?", then two options: **1. Try my bot** and **2. Make changes**, then "(or just tell me what to change 🙂)" The history entry carries `nav: 'review'`.

The full field menu is not shown in the review. The fuller `formatSummary` (Live/Pending blocks, defaults labeled) remains for UI state and tests and is not pasted into chat.

**Prices (prompt only, not enforced):** the prompt tells the model to store each `services[].price` with its currency and unit as the owner said them (e.g. "200 ILS per 60-minute lesson"), never invent either, ask once when a bare number is unclear, and put the missing part in `unknowns` if the owner doesn't know. The review shows the price text exactly as stored; the app does not add or check currency/unit.

## Unknowns, contradictions, and corrections

The prompt tells the model not to invent facts (including not inventing `ownerGoal`). If the owner says something is undecided, unknown, or “not sure yet”, the model is told to put a clear statement in `unknowns` and keep the known parts in the normal fields. In the stored draft, null means a text field is unknown. In the model delta, null means unchanged this turn. The prompt tells it to notice contradictions and ambiguous spots gently.

On a correction or a later clarification, the prompt tells the model to update the draft immediately, drop resolved unknowns, set ready for review, and reply with a one-sentence acknowledgment only (the app shows the review and the two options). Code does not read the owner's wording to detect contradictions, unknowns, or corrections. After the draft merge, if any **already-stored** value was modified or removed (structured old/new draft diff), the app runs a second structured call (`runConsistencyPass` in `src/builder.js`) with that change list and the current draft; it returns extra deltas / `factEdits` for other stored text that still states an old fact. Those updates are applied as app-owned (`applyConsistencyUpdates` — not subject to `preserveFacts`). The pass does **not** run when the turn only adds new facts. It does not set `readyForReview` or force a review (a mid-question turn stays a question). If the call fails, the turn's draft is kept as-is. **Not enforced:** that the second call finds every stale sentence. On approval it copies a valid `ownerGoal` value, a non-empty `ownerGoalRequested`, and non-empty text fields (including `tone`, `assistantName`, `openingMessage`; identity fields also clear on an explicit reset flag) and non-null normalized behavior enums (`responseLength`, `priceDisclosure`), and replaces services, common questions, information to collect, unknowns, and other facts only when the draft includes those arrays. Approval applies every field `mergeDraft` produces to the live profile (no separate field list). A null or blank text field does not clear a value already stored. An omitted array leaves the previous list in place. A null `informationToCollect` in the draft does not clear a previously settled array. A null or invalid behavior enum in the draft does not clear a previously settled setting (see reconcile + merge).

If the model reply is not valid JSON, or structured outputs refuse, the app keeps the previous draft.

**Structured response (app-enforced, OpenAI `json_schema` strict).** Every Builder turn must return all top-level keys (`message`, `draft`, `newFacts`, `ownerEdits`, `factEdits`, `resolvedUnknowns`, `configRequests`, `askingTopic`, `goalSupported`, `goalUnsupportedPart`, `readyForReview`, `asksQuestion`, `wantsReview`). `asksQuestion` is true only when that reply asks the owner a question they are expected to answer (the app stores it on the assistant history entry). `wantsReview` is true only when the owner asked to see the current bot, summary, or review. `draft` has a fixed field list and does **not** include `newFacts`, `otherFacts`, or `askedTopics`. Arrays that are unused this turn are empty; unused text/enum fields are null. The `newFacts` schema describes the array as including owner-stated limits (offerings or areas they do not provide or serve). **Not enforced:** that a required key contains the fact the owner stated — the model can still return `newFacts: []`. The app sets `asksQuestion` true when it substitutes a required-topic question, and false when it presents a review. The owner-facing summary is always `renderReview` of the saved draft — never the model's `message`.

**Draft delta (app-enforced, `applyDraftDelta` / `applyBuilderModelOutput` in `src/builder.js`).** Null (or omitted) text/enum fields mean unchanged. `services` / `commonQuestions` are upserted by identity (`name` / `question`): an empty array means no list changes this turn; a partial list updates or appends those items and keeps the rest in their previous order. `informationToCollect` is replaced only when the model returns an array (`[]` = collect nothing). A non-empty intake array restores any omitted previous items (then appends new ones). `unknowns` arrays are new undecided items only (appended; exact duplicates skipped). Reset flags still clear `assistantName` / `openingMessage` when true.

**Fact preservation across turns (app-enforced, `preserveFacts` / `applyFactOps` / `dropResolved` in `src/builder.js`).** Each turn the model also returns `ownerEdits` (stored services, FAQ entries, or `name` / `whatWeDo` / `hours` / `locationOrArea` that the owner's current message changes or removes), `factEdits`, and `resolvedUnknowns`. Code then:
- Restores a stored service (matched by name) or FAQ (matched by question) that the model dropped, in its previous position, and reverts a changed `price`, `notes`, or `answer`, unless `ownerEdits` covers that item **or** the raw delta proposed that same item this turn (so a one-item price correction still applies when `ownerEdits` is empty). Text fields (`locationOrArea` included): a change that still contains the whole previous value (adds detail only) is accepted; a shortening (the previous value still contains the new one) is reverted unless `ownerEdits` names that field; a rewrite proposed in this turn's delta (neither value contains the other) is kept even when `ownerEdits` is empty.
- Matches a list `ownerEdits.item` only when it is the same stored key, or when it is an abbreviation that overlaps **exactly one** stored item. A null / blank `item` on `services` / `commonQuestions` is ignored (it does not mark every row edited).
- Owns `otherFacts` (off-schema facts, policies, caveats, shown in the order they were stated). The model never re-emits the list. It sees it numbered in the context and returns top-level `newFacts` (appended, exact duplicates skipped) and `factEdits` (`{index, text}` replaces; `text: null` removes).
- Keeps stored `unknowns`, appends any new ones from the delta, then removes the stored unknowns listed in `resolvedUnknowns`.
- **Not enforced:** that the model reports edits correctly. An edit it fails to report is reverted (unless additive), and an edit it wrongly reports is not protected. Which field a fact lands in is up to the model.

## Review, `/test`, `/end`, and later edits

The owner reads the acknowledgment, the summary lines, and the two options (Try my bot / Make changes). **Only the app approves** (enforced): the Builder JSON has no approval field, and typed words such as "approve", "looks good", or "yes" are ordinary Builder messages (they may update the draft or lead to a new review, but never apply it). **Application review gate (enforced, `applyReviewGate` in the session after every Builder turn):**
- When the app presents a review, it stores `reviewedDraftKey` on the profile: a hash of the rendered pending configuration (same fingerprint as before, from the full facts block).
- Approval happens only through **Try my bot** (review option 1, the phrase `Try my bot`, or the editing menu's Try my bot item) while a review of the current draft is pending (`reviewPending`: the stored key matches the current draft, the draft meets the identity/offering minimum, intake is answered, and the bot is either not yet approved or the draft differs from live).
- Any later draft change produces a different key, so the earlier review no longer counts. In particular, a short “yes” that accepts an offered setting alternative keeps that new draft as pending and presents a review of it; the owner then picks **Try my bot**. The app shows the cut-down acknowledgment (filler like "approve when ready" is dropped), the list of what will change, and the two options.
- The gate always keeps the turn’s draft (so accepting an alternative can update the pending configuration).
- **Settings-only edits:** when the business is already approved and the draft changes only conversation settings or identity (business facts equal), the app presents the review even if the model asked an unrelated question instead. Missing `ownerGoal` does not block the preview. The model's question text is stripped; the owner sees the acknowledgment, what will change, and the two options.
- If a required topic is still open (first-time setup), its fixed question is shown instead of a review (including when the model set `wantsReview`).
- **Owner asked to see the summary (`wantsReview`):** same presentation path as `readyForReview` (intake must be answered; required topics still win). If the model did not also set `readyForReview`, the model's `message` is dropped so the owner sees only `renderReview`. If both flags are set, `reviewAck` still applies when the draft key changed. Q&A stays a count (`N answers`), not the stored answers.

`/test`, `/end`, and `/reset` are exact chat commands handled by the app, not the model. `/test` needs `approvedAt` only. Before anything is approved, `/test` replies that nothing is live yet and to choose **Try my bot** on the review. It switches to TEST mode, starts a new customer conversation, and answers each message with the Business Bot (see Business Bot replies). TEST chat does not change the approved profile. `/end` switches back to BUILD. For an approved bot it says the owner is back in editing mode and shows the editing menu (below). Before anything is approved it shows a short "still in first-time setup" line with no menu. It does not clear the approved profile. `/reset` wipes the saved profile and the chats; the next non-command message wakes the fixed welcome again.

## Editing menu (app-enforced, `src/ownerNav.js`)

Applies in BUILD mode. **Menu words** (`menu`, `/menu`, …) require `approvedAt`.

- **Review options (every review, including before first approval):** while the last navigation the app showed is still the review (`lastShownNav` is `'review'`), `1` or `Try my bot` = **Try my bot**, and `2` or `Make changes` = **Make changes**. Later Builder replies that have no `nav` (a correction acknowledgment, a customer-style answer) do not clear that. Exception: if the latest assistant turn has no `nav` and `asksQuestion` is true, a bare `1` or `2` is sent to the Builder as the answer to that question; the option labels still select the review action. Courtesy closers and answers do not set that flag. Anything else goes to the Builder model. **Make changes** replies "What would you like to change?" plus the full editing menu below (`nav: 'menu'`), saves nothing, and works before first approval too, so the menu numbers then work during first-time setup. **Try my bot** behaves exactly like the editing menu's Try my bot item below. Before any review, menu words and bare numbers still go to the Builder model as normal messages.

- **Menu:** rendered from fixed templates (no LLM call), numbered from 1 in this order: 🚀 Get this bot for my business (only when offered, see below), 🏪 Edit business info, ❓ Edit Q&A, 💬 Edit how the bot talks (style, name, opening message), 🤖 Try my bot. Bot goal (`ownerGoal`) and `informationToCollect` stay in the data model, the Builder interview, and the review summary; they are not a menu item — the owner changes them by writing what they want. When the lead item is shown (approved, no lead submitted yet) the menu has five items and Try my bot is 5. Otherwise (before first approval, or after the lead was submitted) it has four items: 1 🏪 Edit business info, 2 ❓ Edit Q&A, 3 💬 Edit how the bot talks (style, name, opening message), 4 🤖 Try my bot. It ends with a line saying the owner can pick a number or just write what to change.
- **When it is shown:** after the owner picks **Make changes** on a review; after `/end`; when an approved owner sends a short menu request (whitelist: `menu`, `/menu`, `main menu`, `show menu`, `back to menu`, `options`, and close variants); and on the first BUILD message after a completed lead questionnaire. Longer phrasings go to the Builder model.
- **Numbers:** a standalone number within the menu's item count is a menu choice only when the latest assistant entry in the Builder history is a menu (the entry carries `nav: 'menu'`; Supabase `build_history` is jsonb, so the marker persists). After any other reply (a section view, a Builder question), a number is passed to the Builder model as an answer. Rendering and parsing share one item list (`menuItems`), and the lead item's visibility is evaluated with the same rule at parse time, so a number maps to the item the owner was last shown. Numbers outside the current item count go to the Builder model.
- **Edit items:** show the current values of that section's existing fields, then ask what to change. Before first approval they show the **merged draft**. After approval they show live values; if an unapproved draft changes that section, live and pending are shown separately. The section view is titled with the plain section name (e.g. "Business info", no number). Business info: name, what the business does, services, hours, location, unknowns, other facts (one line each, only when there are any). Q&A: `commonQuestions`. How the bot talks: tone, reply length, price disclosure (defaults marked as default), assistant name, opening message.
- **Get this bot for my business (app-enforced, `src/leadIntake.js`):** listed as item 1 only when `approvedAt` is set and this sender has not yet submitted a lead. It is not part of the review options. Picking it starts with a short fixed intro plus the contact-consent question, then (after Yes or No) a short bridge and the remaining four questions (no LLM; numbers only, invalid input re-asks; one free-text follow-up for Other on channels, actions, and chat tools). Questions: consent to be contacted on this number, channels, actions, daily inquiries, and current chat tools. Numbered options are shown with a leading emoji; stored /admin answers keep the plain label (no emoji). State lives in `session.leadIntake` (`easybot_sessions.lead_intake`), never in the Builder history, profile, or draft. `/end`, `/test`, `/reset`, or a menu request mid-questionnaire drops it without saving. On completion the app saves one row per sender to `easybot_leads` and replies with a single thanks line based on the stored consent answer (contact-yes: "Thanks! We'll get back to you soon 🙏"; contact-no: "Thanks! We got your details 🙏") and no menu. The next BUILD message (not `/test`, `/end`, or `/reset`) shows the editing menu without the lead item and writes it into Builder history (`nav: 'menu'`), so `1` becomes Edit business info again. After submission it cannot be picked again (if reached, the app replies that the request was already sent). Before first approval the lead item is not listed, so `1` is Edit business info and `5` goes to the Builder model.
- **Try my bot (5 with the lead item, otherwise 4):** if a review of the current draft is pending (`reviewPending`: matching `reviewedDraftKey`, intake answered, enough for a first bot, and either not yet approved or draft differs from live), the app **approves that draft** and enters TEST ("Bot updated ✅" + the TEST-mode line). If no review is pending, it is the same path as `/test` (same prerequisites and refusal replies).
- **Read-only (edit items and menu words):** showing the menu or a section never saves the profile, so it does not change the draft, does not invalidate `reviewedDraftKey`, and approves nothing. **Try my bot** with a pending review is the exception (it approves). Navigation turns are appended to the Builder history so a follow-up like "make it warmer" has context. Free-text edits work at any time, including right after a section view of a different topic. Edits still go through the draft, review, and approval gate above.
- **Not verified:** that the model's own acknowledgment never contradicts the app's approval result.

A later edit in BUILD is another interview turn. The prompt tells the model to update the draft and leave it unapproved until the owner confirms (one-sentence acknowledgment; the app shows what will change plus the two options). The pending draft is saved immediately; the live fields and the Business Bot stay as last approved until the owner approves a review with **Try my bot**. Behavior-only edits (tone / length / price disclosure / assistant name / opening) follow the same draft → review → Try my bot → live path and must not change business facts. The app also enforces the preview through the settings-only rule of the review gate.

**Customer prompt structure (enforced by `buildCustomerSystemPrompt`):** APPROVED BUSINESS FACTS, BOT OBJECTIVE, CONVERSATION SETTINGS (tone, length, price policy, assistant identity / opening — with a priority statement that settings never establish facts/capabilities/intake), then BEHAVIOR RULES (closed-world contract wins on conflict). Approved identity and opening live inside conversation settings, separate from business facts. Absence of an approved fact is a gap (prompt-only: name the missing info as not available here, not “I don’t know”; warmly invite messaging the owner only when a real gap remains, never promising a response; never treat silence as yes or no). A stated pricing process is a complete answer. After listed intake is in the chat, confirm it; do not send the customer elsewhere because the chat cannot book. Not enforced.

**Approval is instant (enforced):** On approval (**Try my bot** with a pending review) the app saves the approved fields with a new `approvedAt`. Nothing else has to finish first: there is no external sync, pending state, or background worker. It then enters TEST immediately.

**Business Bot replies (enforced):** each TEST message is one OpenAI chat completion from the app (`businessBot.js`): model `OPENAI_MODEL` (default `gpt-4o-mini`), the system prompt from `buildCustomerSystemPrompt` on the live approved profile, then the last 20 messages of the TEST conversation, then the new message. Classic models are sent at temperature 0. If the model rejects temperature (typical of reasoning models), the app retries without it, with `max_completion_tokens` and the lowest `reasoning_effort` that model accepts (`none`, then `minimal`, then `low`). The working shape is cached per model name. Default model is still `gpt-4o-mini`. The TEST conversation is the session's `testHistory` (Supabase `easybot_sessions.test_history` for WhatsApp, so it survives restarts and deploys). The app keeps the last 40 messages and clears it on each `/test`. If the OpenAI call fails, the owner gets "Sorry, your bot couldn't answer right now. Please try again in a moment."; the failed turn is not added to the history and provider error text is neither shown nor logged. Owner-facing app messages use plain product wording with no internal service names, URLs, or raw error text. If the WhatsApp worker gets no reply, it sends a generic "Sorry, something went wrong…" message. These templates are enforced; model-generated Builder and Business Bot replies avoiding internal names is a prompt-level expectation only and is not enforced or verified.

**Browser / local:** profile file on disk; session transcript in memory (file-backed sessions). **WhatsApp:** each sender has isolated session + profile + inbound queue in Supabase (`easybot_*` tables). The Twilio webhook validates `X-Twilio-Signature`, enqueues by `MessageSid`, ACKs quickly, and a durable worker processes messages in order per sender. **Unverified:** that the model always waits for confirmation, preserves every unknown, stores full FAQ answers (not truncated paraphrases), leaves `ownerGoal` unset until clarified, splits FAQ vs intake correctly without the gate, maps style/price-disclosure natural language reliably, or treats “yes” only as approval after a summary.
